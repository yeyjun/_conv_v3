# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Windows Forms point-of-sale / inventory app ("BrewCode", store name "Baclig Minimart") targeting .NET Framework 4.7.2, backed by a remote MySQL database. `_conv.sln` has six projects: `Inventory` (the POS app itself), `RemoteController` (a standalone companion tool - license key generation and network status/activation, see below), `Remittancce` (a standalone "send money" / padala counter tool, see below), `InfraMonitor` (a standalone local terminal health dashboard, see below), `ItemMonitor` (a standalone ASP.NET Core web dashboard for item stock levels, see below - the only web/non-WinForms project, and the only one targeting modern .NET (net8.0) rather than .NET Framework 4.7.2), and `Launcher` (a small picker that starts whichever desktop app - Inventory, Remittancce, or InfraMonitor - the user picks; `ItemMonitor` is a web app with no `.exe` to launch this way, so it isn't in `Launcher` or the installer, and is run/deployed independently, e.g. `dotnet run` or published to a web server).

## Build

This is a classic .NET Framework project (packages.config), so use `msbuild`/`nuget`, not `dotnet`:

```powershell
nuget restore _conv.sln          # or let Visual Studio restore packages/
msbuild _conv.sln /p:Configuration=Debug
```

Output: `Inventory\bin\Debug\BrewCode.exe`. If `msbuild` isn't on PATH, use the VS 2022 Developer PowerShell or the full path under `C:\Program Files\Microsoft Visual Studio\2022\`.

`FreshData.cs` at the repo root is a solution item only — it is not compiled into the project (and doesn't compile as-is; its `using MySql.Data.Client` is wrong).

## Architecture

- **`Form1.cs` contains the main form, class `Purchases`** (namespace `Inventory`) — the name/file mismatch is easy to trip on. `Program.Main` runs `Purchases` directly; `Login`, `PinPromptForm`, and the other forms are opened from it. Most business logic (sales, receipts, held transactions, printing) lives in this ~2,200-line file.
- **`DataCacheManager.cs`** (namespace `YourApp.Data`) is a singleton cache of `DataTable`s loaded from MySQL once at startup (`LoadAll()` in `Program.Main`). Forms read via `GetTable("Items")` / `GetTable("Users")` instead of querying the DB. Successful loads are snapshotted to `Documents\App Inventory\OfflineCache\*.xml`; if the DB is unreachable the app runs in **offline mode** from the snapshot (`IsOfflineMode`, `OfflineSnapshotAsOf`). When adding a table the app needs at startup, register it in `LoadAll()`.
- **`ActivityLog.cs`** writes audit events to the `logs_` table, falling back to `Documents\App Inventory\OfflineCache\PendingActivityLogs.log` when offline (meant to be replayed manually later).
- **`OperationLog.cs`** is a separate, always-on XML audit trail of every create, read/scan, update, delete, and login app-wide, plus completed sales - written unconditionally regardless of whether that operation's own DB write succeeded. One file per day (`Documents\App Inventory\OfflineCache\Operations\yyyy-MM-dd.xml`); each operation gets its own `<Operation id="OP#" module="...">` element inside that day's file, numbered by scanning the highest existing id rather than an in-memory counter, so numbering stays correct across restarts within the same day. `module` is the form/class that performed the operation, passed explicitly by each caller (e.g. `nameof(Purchases)`) rather than inferred from the call stack - Form1.cs's main form is actually named `Purchases`, so a file-name-derived module tag would be misleading there. Current call sites: `Login.cs` (`RecordLogin`, success and failure), `AddItemForm.cs` (`RecordCreate`), `ManageUsersForm.cs`/`LoyaltyForm.cs` (`RecordCreate`/`RecordUpdate`/`RecordDelete`), `PettyCashEntryForm.cs` (`RecordCreate`), `TaxConfigForm.cs` (`RecordUpdate`), `Form1.cs` (`RecordRead` on every item scanned into the cart, `RecordUpdate`/`RecordDelete` from the Manage Prices tab, `RecordSale` from `SaveSaleLineItemsAsync`), and `Program.cs`/`ScheduledReportService.cs` (`RecordAction`, alongside their existing `ActivityLog.LogAsync` calls).
- **Direct DB access pattern:** forms build MySQL connection strings from `App.config` appSettings (`DB_SERVER`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `CONNECTION_TIMEOUT`) and run parameterized `MySqlCommand`s inline — there is no ORM or repository layer. Tables in use: `items_`, `user_`, `sales_`, `customers_`, `loyalty_transactions_`, `pettycash_`, `logs_`, `app_config_` (note the trailing underscores).
- **`AppConfigService.cs`** reads/writes `app_config_`, a shared key/value table — unlike everything else, which is per-machine `App.config`, a row written here is visible to every terminal on the same database. `EnsureTableAsync` creates this table on first use (not just via System Config > Database Setup), because a table literally named `setting_` (this table's original name) already existed on real production databases with a completely unrelated shape (`id`/`description`/`switch`/`switch2`/`switch3`, not a key/value store) — every read/write against it was silently failing (writes threw, and reads hit the fail-open catch block below and silently always reported values as unset/off). Renamed to `app_config_` to stop colliding with that table. Currently used for **system maintenance mode** (`MAINTENANCE_MODE`/`MAINTENANCE_MESSAGE` keys, toggled from System Config > Maintenance): `Program.cs` checks it at startup and blocks with `MaintenanceForm` (same pattern as `TrialExpiredForm`) if on, and `Purchases` also polls it every 2 minutes (`StartMaintenanceWatcher` in `Form1.cs`) so a terminal already running gets blocked too. Either gate can be bypassed with the `ADMIN_PIN`. Also used for the **low-stock reminder** (`LOW_STOCK_REMINDER_ENABLED`/`LOW_STOCK_THRESHOLD`/`LOW_STOCK_REMINDER_INTERVAL_MINUTES` keys, toggled from System Config > Low Stock Reminder): `Purchases` polls it every 2 minutes (`StartLowStockReminderWatcher` in `Form1.cs`), and when enabled and due (per the configured interval), shows a centered, non-gating `LowStockReminderForm` listing every item in the cached Items table at or below the configured quantity threshold. Reads fail open (treated as "off"/defaults) on any DB error, per the offline-resilience convention below.
- **Manager overrides** (voids, sensitive actions) are gated by `PinPromptForm` against the `MANAGER_PIN` appSetting.
- **`AppFonts.cs`** loads embedded fonts (e.g. Morally Serif) into a `PrivateFontCollection`; labels using them need `UseCompatibleTextRendering = true` because GDI can't see memory fonts.
- Each feature is a separate WinForms form (`AddItemForm`, `ListSales`, `InventoryReport`, `LoyaltyForm`, `PettyCash`, `TellerHistoryForm`, `HeldTransactionsForm`, `ManageUsersForm`, `SalesChartForm`, `GenerateBarcode`, `printable`), each with a `.Designer.cs` — keep control layout changes in the Designer file as Visual Studio expects.
- **`TrialLicense.cs`** gates new installs behind a per-machine trial (`TRIAL_ENABLED`/`TRIAL_DAYS`, local start-date file), lifted by a per-store license key (`LICENSE_KEY` appSetting, or an AES-encrypted `.tmrgo` file via `TryActivateFromFile` - opening one in Notepad shows ciphertext, not the key) validated against a salted hash of `STORE_CODE`. Enforced at startup in `Program.cs` via `TrialExpiredForm`. A terminal already running past that point (left open across the trial or an activated key's own expiry date) isn't gated by the startup check alone: `TRIAL_AUTO_CLOSE_ENABLED` (System Config > Trial / Licensing, off by default) makes `Purchases` poll `TrialLicense.IsExpired`/`HasExpiredLicenseKey` every 2 minutes (`StartTrialExpiryWatcher` in `Form1.cs`, same polling pattern as `StartMaintenanceWatcher` but purely local - no DB round trip) and close itself once either goes true.
- **`RemoteControlServer.cs`** is an off-by-default (`REMOTE_CONTROL_ENABLED`), token-authenticated (`REMOTE_CONTROL_TOKEN`) TCP listener (`REMOTE_CONTROL_PORT`, reachable over LAN or, with router port-forwarding, the public internet) with a deliberately tiny, non-destructive command set (`PING`/`STATUS`/`ACTIVATE`/`GET_MENUS`/`SET_MENUS`) — see System Config > Remote Control. `SET_MENUS` writes `HIDDEN_MENUS` the same as System Config > Menus and immediately calls `ApplyMenuVisibility()` on the live `Purchases` window (found via `Application.OpenForms`, marshaled onto the UI thread) so a remote menu change takes effect without a restart. TCP connections are TLS-wrapped using a self-signed cert (`RemoteControlCertificate.cs`, generated via BouncyCastle - already a transitive dependency, so no new package was needed there - and cached at `Documents\App Inventory\OfflineCache\RemoteControlCert.pfx`); its thumbprint is shown in System Config for trust-on-first-use pinning in RemoteController. Repeated bad tokens from the same remote address get a temporary lockout (in-memory, per `RemoteControlServer`'s own tracking - resets on app restart). `BluetoothControlServer.cs` is a second, off-by-default (`REMOTE_CONTROL_BLUETOOTH_ENABLED`) listener reusing the exact same command handling over RFCOMM instead of TCP (no TLS there - OS-level Bluetooth pairing is its own trust step); it needs `InTheHand.Net.Bluetooth` (32feet.NET), vendored manually into `packages\` since this sandbox has no `nuget.exe` (see `packages.config` in both projects) - never assume Bluetooth actually works end-to-end without testing on real hardware, since no radio was available to verify it here. The `RemoteController` project is the client/counterpart for all of this: it has **no project reference** to `Inventory` on purpose (meant to be handed to someone who only issues licenses, not build the POS app), so it duplicates the license-key algorithm and wire protocol - keep both copies in sync by hand if either changes.
- **`RemoteController\MainForm`** is a `TabControl` with three pages: License, Remote Control, and Fleet. **Fleet** (`FleetStore.cs`, `FleetEntryForm.cs`) is a purely local, per-machine list of known terminals (`Documents\RemoteController\Fleet.xml` - no server, doesn't sync between copies of RemoteController) - Store Name/Host/Port/Token/Latitude/Longitude, shown in a `DataGridView`. "Refresh All" PINGs every entry with its saved token (`FleetStore.CheckStatusAsync`), so status is really "Online" (correct token) vs "Reachable (bad token)" vs "Offline" (no connection at all), not just a port scan. `FleetEntryForm`'s "Detect (approximate)" button is an optional convenience that geolocates the entered host via `ip-api.com` (city-level accuracy at best, meaningless for a private/LAN address) - coordinates are always manually editable and never treated as authoritative.
- **`Remittancce`** is a second standalone companion app (own `.exe`, no project reference to `Inventory` - same reasoning as `RemoteController`) implementing a "send money" / padala counter service: the store acts as a remittance agent (GCash, PayMaya, Palawan Express, Cebuana Lhuillier, Western Union, or a custom provider). `RemittanceHistoryForm` is its main window (date-filtered ledger, CSV export, a `Teller` field defaulting to `Environment.UserName` since there's no login system here); `RemittanceEntryForm` is the entry dialog, opened via its "Send Money (F2)" button. Both duplicate `Inventory`'s `ErrorDialog` pattern and DB connection string building rather than sharing code. `UiStyle.cs` defines its own "ink ledger" palette (navy/cream/vermilion, Consolas for money figures) distinct from `Inventory`'s look. Reads/writes the `remittance_` table on the same production DB (own `App.config` copy of the DB credentials - another place those credentials now live, see below).
- **`InfraMonitor`** is a fifth standalone companion app (own `.exe`, no project reference to `Inventory` - same reasoning as `RemoteController`/`Remittancce`) that monitors the health of the local PC/terminal it's running on, not any remote server or the MySQL database - it has no DB dependency or `App.config` at all. `MainForm` is a four-tab dashboard: **System Health** (`SystemHealthPanel` - an aggregate Normal/Warning/Critical banner plus machine name, OS version, uptime, memory, and a CPU glance, all via `SystemMetrics.cs`), **Storage Watch** (`StorageWatchPanel` - a `DataGridView` over `DriveInfo.GetDrives()` for fixed drives, flagging Warning at 80% used and Critical at 95%), **CPU Health** (`CpuHealthPanel` - a large live `% Processor Time` readout plus a hand-rolled 60-second sparkline (`SparklinePanel`), flagging Warning at 70% and Critical at 90%), and **I/O Errors and Warnings** (`IoEventsPanel` - scans the Windows "System" event log for Error/Warning entries from disk-related sources like `disk`, `Ntfs`, `volmgr`, and common storage controller drivers; see `IoEventScanner.cs`'s `DiskRelatedSources` list). CPU sampling goes through a single shared `PerformanceCounter` in `CpuMonitor.cs` so the overview and the CPU tab agree. Each of the three sub-tabs exposes a `Status`/`StatusChanged` so `MainForm` can roll them up into the System Health banner (worst-of-three). Event log scanning runs on a background `Task` (capped at 5000 scanned / 200 matched entries) so a large log can't hang the UI; like the rest of the suite, a failure to read the log (e.g. no permission) is caught and shown as a message rather than crashing. Uses its own dark "ops console" `UiStyle.cs`, distinct from `Remittancce`'s ink-ledger look.
- **`ItemMonitor`** is a standalone ASP.NET Core Razor Pages web app (net8.0, SDK-style csproj, `PackageReference`s instead of `packages.config`) - the suite's only web project and the only one not targeting .NET Framework 4.7.2. It shows stock levels read live, read-only, from the same `items_` table. There's no reorder-level column on `items_`, so "low stock" is one configurable threshold (`LowStockThreshold` in `appsettings.json`, default 10 units) applied to every item rather than a per-item value; items at or below 0 are "Out of Stock". `appsettings.json` holds its own copy of the DB_SERVER/DB_NAME/DB_USER/DB_PASSWORD credentials, built into a connection string the same way the WinForms apps build theirs from `App.config` - yet another place those credentials now live (see the standing TODO above).
  - **Data layer** (`Services/ItemStockService.cs`, using the same `MySql.Data` package as the WinForms apps): search/status-filter/sort/pagination all happen server-side in a single SQL query per request (a derived table computes `status` and a `status_priority` severity rank in SQL, so sorting "by status" means by severity, not alphabetically) rather than pulling the ~2,500-row catalog into memory - this matters at this table's real size. Sort column/direction and the status filter are matched against whitelists before touching SQL (`ORDER BY`/column names can't be parameterized); search and the status value itself are passed as real parameters. `GetCountsAsync()` is a separate, tiny aggregate query so the KPI tiles always reflect the *whole* table regardless of the current search/filter. Real production rows don't always match `DbSetupService`'s reverse-engineered DDL cleanly (observed: unparsable `date_of_entry` values, null columns) - row reads are wrapped per-row in try/catch with a `SkippedRowCount` counter rather than letting one bad row blank out the whole page, and a DB connection failure returns an `Error` string surfaced as a banner instead of crashing, matching the rest of the suite's offline-resilience convention as best a live-read-only web page can.
  - **Two callers share that query model** (`ItemsQuery`/`ItemsPage`/`StockCounts`): `Pages/Index.cshtml.cs` does the first server-render (query-string bound, so a filtered/sorted/paged URL is bookmarkable and works with JS disabled), and a minimal API route in `Program.cs` (`GET /api/items`, enums configured to serialize as strings via `ConfigureHttpJsonOptions` so the JS can match them by name) serves the same shape as JSON for everything after that.
  - **Client-side** (`wwwroot/js/dashboard.js`, no framework/build step) hydrates the server-rendered page: debounced search, sortable column headers (real `<button>`s inside each `<th>`, not a bare clickable `<th>`, for keyboard/a11y), click-to-filter, pagination, and state synced to the URL via `history.replaceState`. It polls `/api/items` every 15s (paused via the Page Visibility API when the tab isn't visible, firing immediately again on refocus) to keep the page live without a full reload - there is no `meta http-equiv="refresh"` here. Rows are built with `createElement`/`textContent`, not `innerHTML` string concatenation, since item descriptions come from the live DB and shouldn't be trusted as HTML.
  - **Visual design** (`wwwroot/css/site.css`) is a deliberate "warehouse shelf-tag" language distinct from both `Remittancce`'s ink-ledger look and `InfraMonitor`'s cool ops-console look: a warm near-black palette (not cold black), Oswald for the condensed warehouse-signage display type, Inter for body text, IBM Plex Mono for all figures (quantities, prices, timestamps). The one signature shape - a notched "price tag" silhouette via `clip-path` - is reused for both the KPI tiles (which double as the status-filter buttons, tying the stat display and the filter control into one object) and the per-row status chip, so the shape carries real meaning everywhere it appears rather than decorating just one spot.
- **`Launcher`** is a small project - three buttons, "Inventory", "Remittance", and "Infra Monitor" - that starts the corresponding sibling `.exe` via `Process.Start` and closes itself immediately. `FindExePath` in `LauncherForm.cs` supports two different layouts: installed (its sibling app's folder sits right next to its own, `{app}\<ProjectFolder>\<exe>`) and dev build (walking up from its own `bin\<Configuration>` folder to the repo root, then into `<ProjectFolder>\bin\<Configuration>\<exe>`, trying its own configuration first, then Debug, then Release) - it tries the installed layout first, then falls back to the dev one.
- **`installer\AppInventory.iss`** (Inno Setup) packages all four apps - `Inventory`, `Remittancce`, `InfraMonitor`, and `Launcher` - each into its own subfolder under `{app}` (required: `Launcher`'s installed-layout lookup above depends on that exact sibling-folder structure, so don't flatten it). The Start Menu/Desktop shortcut and post-install "Launch" checkbox point at `Launcher.exe`, not at any app directly. Build all four in Release first (`msbuild _conv.sln /p:Configuration=Release`), then compile the script with `ISCC.exe`.

## Conventions and gotchas

- Offline resilience is a deliberate design goal: DB failures should degrade to cached/snapshot data or local log files, never crash the app. Follow that pattern for new DB-touching code.
- Real production DB credentials and the manager PIN currently live in `App.config` — be careful not to spread them further (there's a standing TODO to move them out).
- ClickOnce publish settings live in the csproj (`PublishUrl` etc.); don't disturb them when editing the project file.
- Receipts/exports use ClosedXML (Excel), Aspose.PDF, and raw `System.Drawing.Printing`.
