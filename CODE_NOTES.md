# Code Notes

Explanatory comments removed from the source during this session's cleanup, consolidated here so the reasoning isn't lost. Organized by file, then by the method/member each note was attached to.

## Inventory/AddItemForm.cs

- **btnSave_Click, conn.OpenAsync catch**: The database itself is unreachable (not a bad INSERT) - queue the item locally instead of losing it. It's merged into the live cache immediately so it can be rung up for a sale this session, and re-merged on every future load until it's actually inserted and synced (see PendingItemStore).
- **btnSave_Click, INSERT catch**: The database IS reachable here - this is a real failure (e.g. duplicate barcode), not an offline condition, so it's surfaced as an error rather than queued.

## Inventory/CalculatorForm.cs

- **CalculatorForm**: <summary> When opened with items already in the cart, <paramref name="initialValue"/> (the cart's sum of prices) is shown pre-loaded on the display instead of "0", ready to be used as the first operand - matching how a calculator's memory-recall normally behaves, any digit typed next starts a fresh number rather than appending to the recalled one. </summary>
- **foreach (Control control in Controls)**: All keyboard input is handled centrally by CalculatorForm_KeyDown, so none of the buttons need to be reachable via Tab. More importantly, a focused Button always consumes Enter for itself (standard Windows behavior - AcceptButton doesn't override that), so leaving one focusable meant pressing Enter to "equal" could also silently re-click whichever button still held focus (e.g. the initially-focused Clear button), resetting the result right back to 0 straight after computing it correctly.
- **}**: Deliberately a no-op here - see CalculatorForm_KeyUp, which is where Escape actually closes the form.
- **e.Handled = true;**: Handled (not just SuppressKeyPress) is required here: SuppressKeyPress only blocks the follow-up KeyPress/WM_CHAR, it does NOT stop the key from still reaching whatever control currently has keyboard focus. Since keyboard-only input never moves focus off the dialog's first focusable control (btnClear), an unhandled Enter would also re-trigger that still-focused button's own Click right after this handler computed the real result - silently resetting the display back to 0.
- **CalculatorForm_KeyUp**: <summary> Escape closes the calculator on KeyUp rather than KeyDown so the whole press-and-release of that physical key is consumed here, by the still-open calculator, instead of the KeyDown closing the form immediately and leaving the matching KeyUp to land on whatever control regains focus on the underlying Purchases window (e.g. the cart grid, whose own Escape-on-KeyUp handler clears the entire cart). Every other keyboard shortcut in this app is likewise wired to KeyUp rather than KeyDown for the same reason. </summary>

## Inventory/DataCacheManager.cs

- **_lastUpdated field**: When each table's data was last known-fresh - a live pull just now, or (if the DB was down at the time) the offline snapshot file's own save time. Left untouched when a load falls back to an already-in-memory copy, since that copy's data is exactly as fresh as whenever it actually was last loaded, not "now".
- **LoadTable (end, before returning)**: Re-layer any items added locally while offline (AddItemForm/PendingItemStore) on top - whichever path just populated _cache["Items"], from a live DB pull, the kept-in-memory copy, or the offline snapshot, so they don't disappear until someone actually inserts them for real and removes the matching entry from the pending queue.
- **MergePendingItemsIfApplicable**: Merge into a copy and swap it in (rather than mutating table in place) so any already-running lookup that caches the table reference - e.g. Purchases.FindItemRow's serial index - sees a changed instance and knows to rebuild instead of serving stale results from before the pending items were merged.
- **GetLastUpdated**: When the given table's data was last known-fresh - either a live DB pull or (if that table is currently being served from the offline snapshot) the snapshot file's own save time. Null if that table has never been loaded at all. Used e.g. by the main form's title bar to show stock staff how old the on-screen item data might be while the database is unreachable.
- **ItemRowHasIntegrityIssue**: True if this Items row is missing a usable serial (can't be scanned/looked up at all) or has no positive price in any of the three pricing tiers (would ring up for free, or not at all) - a reasonable sign of corrupt/incomplete data that would misbehave if sold against while offline. Exposed so both the main form's cache status indicator and InventoryReport's per-row flagging share one definition instead of drifting apart.
- **HasPositivePrice's catch**: Unparseable value is no more usable than a missing one.
- **CountItemIntegrityIssues**: Counts Items rows currently failing ItemRowHasIntegrityIssue - 0 if Items hasn't been loaded yet.
- **ReplaceTable**: Swaps in a replacement DataTable for an already-loaded key - used by PendingItemStore so a newly queued offline item shows up immediately. Callers that cache the table reference themselves (e.g. Purchases.FindItemRow's serial index) only rebuild when the instance actually changes, so mutating the existing table in place wouldn't be picked up without a restart; replacing it here forces that rebuild on the very next lookup.

- **UsesAutomaticLayout**: A control that's Docked, or Anchored to anything other than the default Top-Left, is already repositioned by WinForms itself whenever its parent resizes (e.g. the Quantity textbox is anchored Top|Right so it stays near the right edge at any window size). Forcing an absolute Location/Size on one of these fights that built-in layout: it looks right only by coincidence, for whatever window size the position happened to be saved at, and can end up off-screen - effectively "missing" - at any other size or on a later resize. Such controls are skipped entirely so they keep following their own anchor/dock layout.
- **ClampLocationToParent**: A position saved on a bigger window/screen (or before a resize) could otherwise place a control partly or fully outside its parent's visible area - effectively "hidden" even though it's technically still there. Keeping at least a sliver on-screen means it can always be found and dragged back into place from Edit Layout mode, rather than needing this file deleted by hand to recover.
- **ClampSize**: Never smaller than MinControlSize, regardless of what's in the file - a 0x0 (or negative) restored size would make a control permanently unreachable to fix by hand.
- **int? width = (int?)control.Attribute("width");**: width/height are optional - absent on entries saved before resizing existed, or for a control that was only ever moved, never resized. Either way that means "leave the current (Designer-set) size alone".
- **}**: Best-effort only - a missing/corrupt file just means no saved layout to restore.

## Inventory/OperationLog.cs

- **OperationLog**: <summary> Durable, always-on XML audit trail covering every create, read/scan, update, delete, and login in the app, plus completed sales - written unconditionally, independent of whether that operation's own database write succeeded (see ActivityLog.LogAsync and Purchases.SaveSaleLineItemsAsync, which both call this regardless of outcome).  One file per calendar day (Documents\App Inventory\OfflineCache\Operations\yyyy-MM-dd.xml). Each operation inside it gets its own &lt;Operation id="OP#" module="..."&gt; element, numbered incrementally within that day's file (restarting at OP1 the next day) - the number is derived from the highest id already in the file rather than an in-memory counter, so it stays correct across app restarts within the same day. "module" is the form/class that performed the operation (e.g. "Purchases", "AddItemForm") - passed explicitly by each caller rather than inferred from the call stack, since Form1.cs's main form is actually named Purchases (see CLAUDE.md) and a file-name-based module tag would be misleading there.  The file keeps the ".xml" name but its bytes on disk are AES-encrypted (see EncryptFile/DecryptFile) - opening one directly shows ciphertext, not plaintext sale/login/ CRUD details, the same reasoning and AES setup as TrialLicense.cs's .tmrgo files. Unlike those, the IV here is random per save (prepended to the ciphertext) rather than derived from the KDF, since this file is rewritten many times a day rather than written once.  Writes are best-effort and must never block whatever triggered them, same as ActivityLog/LogPendingSale. Guarded by a lock since checkout and background activity-logging can both write around the same time. </summary>
- **FileKeyPassphrase**: Not meant to withstand someone reading the source - only to stop the contents (sales, logins, CRUD details) being casually readable by opening the file in a text editor. Consistent with this app's existing security bar (see TrialLicense.cs's FileKeyPassphrase).
- **ReadRawXml**: <summary>Decrypts and returns today's (or any day's) raw XML text - for a future admin viewer/export, same purpose as MainLayoutStore.ReadRawXml. Not currently wired into any UI. Returns null if the file doesn't exist or can't be decrypted.</summary>
- **root = new XElement("Operations");**: Corrupt/undecryptable file (e.g. hand-tampered) - start fresh rather than silently dropping every new entry for the rest of the day.
- **}**: Best-effort audit trail only - never let this block whatever triggered it.
- **EncryptFile**: IV is random per save and prepended to the ciphertext (rather than derived from the KDF like TrialLicense.cs's one-shot .tmrgo files) since this file is rewritten many times a day - reusing one IV across that many saves of related plaintext is the kind of thing that actually weakens AES-CBC, unlike a license file written exactly once.

## Inventory/PendingItemStore.cs

- **PendingItemStore**: <summary> Items added via AddItemForm while the database is unreachable. Saved to a local XML queue (OfflineCache\PendingItems.xml) so nothing is lost, merged into the live "Items" cache immediately (via <see cref="MergeInto"/>) so the item can be rung up for a sale right away, and re-merged every time that cache is (re)loaded (see DataCacheManager.LoadTable) so it keeps showing up - even across a restart, or if the connection comes back before anyone's inserted it for real - until whoever manages the database does that and removes the matching file entry by hand (mirrors ActivityLog's "replay manually later" convention). </summary>
- **GetLastUpdated**: <summary>When the pending-items queue was last written to (a new offline item, or a quantity adjustment against one) - null if nothing has ever been queued on this machine. Used by Purchases' status bar so staff can see at a glance whether there's offline-only stock waiting to be synced, not just whether the DB is reachable right now.</summary>
- **GetPendingCount**: <summary>How many items are currently queued (added offline, not yet inserted into items_ for real) - 0 if the file doesn't exist or can't be read.</summary>
- **IsPending**: <summary>True if this serial is still only locally-queued (added via AddItemForm while offline) rather than a real row already inserted into items_ - used by InventoryReport to flag "Pending Sync" rows distinctly from ones already confirmed in the database.</summary>
- **Add**: <summary>Queues the item locally and layers it onto the live cache (if loaded) so it's immediately available for a sale in the current session, not just after a restart.</summary>
- **DataTable current = DataCacheManager.Instance.GetTable("Items");**: Merge into a copy and swap it in (rather than mutating the live table in place) so an already-running lookup that caches the table reference - e.g. Purchases.FindItemRow's serial index - sees a changed instance and rebuilds instead of serving a stale result that predates this item.
- **}**: Cache not loaded yet (e.g. called before startup finishes) - the file entry is enough; DataCacheManager.LoadAll will merge it in once the table exists.
- **AdjustQuantityIfPending**: <summary> Applies a stock delta to a still-pending item's own queued quantity, if one exists for this serial - e.g. a sale (or a sale being reversed by removing it from the cart) while offline. Without this, <see cref="MergeInto"/> re-running later (another offline add, a reconnect poll, a restart) would stamp the item's quantity back to whatever it was when first queued, silently undoing every sale made against it in the meantime. No-op if this serial was never queued (i.e. it's a normal catalog item, not a pending one). </summary>
- **SetQuantityIfPending**: <summary>Same as <see cref="AdjustQuantityIfPending"/> but sets an absolute value instead of a delta.</summary>
- **}**: Best-effort only - the in-memory cache (which the caller already updated) stays correct for this session either way; this just keeps the on-disk queue in sync.
- **MergeInto**: <summary>Layers every still-pending item onto <paramref name="itemsTable"/> - adding a new row or overwriting the existing one by "serial", so re-merging after another load never duplicates a row.</summary>
- **}**: Best-effort per item - one malformed/incompatible entry must not stop the rest of the queue (or the table load that triggered this merge) from working.
